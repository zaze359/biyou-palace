# 碧游宫 V2.0 · Super-agent 架构与契约

> 父任务：`10-13-biyou-v1-blueprint`
> 命名基准：[docs/naming.md](../../../docs/naming.md)
> 状态：规划中（V2.0-A / V2.0-B）

## Goal

将 V1.0 的异构推理集群升级为 **碧游宫 Super-agent 系统**：

> 碧游宫是一个道门；阵眼常驻主持，知客堂接缘起，观星研判后立师门任务，派差给异构仙徒，仙徒在洞府中执行并回禀，巡阵负责命灯与恢复，功德殿负责任务交接，观星台供人观测与定夺。

## 产物与形态

- **两条产品线**：桌面客户端（macOS / Windows）与移动端（Android 先行，iOS 同步规划）。
- **默认单机自闭环**；联阵是可选加法，不是前提。
- **桌面端启动默认单机，不自动开阵**；用户主动开阵后才担任阵眼。移动端默认单机，入阵后作为外门仙徒。
- **联阵方式**：局域网「开阵 / 寻阵 / 入阵」，类似魔兽争霸 III 的 LAN 房间列表；无云大厅、无账号、无公网。
- **服务端不是独立交付物**；旧集群降级为联阵后端 / 参考实现。

## Requirements

### R1 命名与术语

- 新文档、新 UI、新契约统一使用 `docs/naming.md` 的规范名。
- 代码/API 仍用英文；现有 `/v1/*` 不因命名改动。
- 关键映射：碧游宫=道门/系统，山门=NewAPI，阵眼=Router，仙徒=Worker，师门任务=Ticket，师门令=Mandate，知客堂=Source，缘起=Trigger，观星=Eval，派差=Assignment，回禀=Report，巡阵=Watchdog，碧游宫客户端=Client，功德殿=Task Hall，观星台=Observe/Approval。

### R2 仙箓与玉册

- 每个仙徒暴露仙箓（Agent Card）：身份、根骨（`root: inner | outer`）、道行、功德、神通、法宝、模型、限额、位置、状态。
- 阵图维护玉册（Registry）：仙徒与信源注册、命灯、租约、神通与法宝索引、最新道行。
- 不要求所有仙徒跑完整 Agent loop；外门仙徒可作为专精型仙徒。

### R3 师门任务契约

- 新增师门任务 API（`/agent/v1/*`），至少包含：
  - 创建/查询师门任务
  - 任务品阶（黄/玄/地/天/宇/宙/洪/荒）、最低道行、风险（清修/入世/破阵/传道）
  - 师门令（范围、期限、强度、法宝、数据边界）
  - 派差与领命
  - 回禀（progress / waiting / ready / blocked / failed / dropped）
  - 取消与超时
- 师门令不可变；扩大范围必须新开师门任务。
- 同一缘起重复受理只生成一个师门任务（幂等）。
- 无合格仙徒时进入「悬赏」状态，不得静默降阶派差。
- 有合格仙徒但忙碌时进入「候差」；V2 不抢占在途低阶任务。

### R4 知客堂与缘起

- 知客堂负责接事、收帖、传讯，保存读取位置与身份；重启不重放。
- 缘起是不可变事件，归属因果线；同一因果线同时只跑一个观星。
- 首批信源：灵脉警讯；后续可加碧游宫客户端目标、定时值守、IM。

### R5 阵眼

- 阵眼常驻，维护全局神识与因果线；只协调分派，不亲自执行具体任务。
- 流程：门规 Gate → 观星 Eval → 师门任务 + 师门令 → 派差 → 回禀 → 功德殿 → 观星台定夺。
- 派差硬规则：不越阶（道行 ≥ 最低道行）、不越权（风险在师门令内）、神通/法宝匹配。
- 高阶可接所有低阶任务，但「可接」只是资格，不是优先权。
- 高阶不轻用：低阶任务优先派给刚好够用的仙徒；高阶仙徒留给高阶任务。
- 不抢占（V2）：高阶任务到达时，若高阶仙徒正执行低阶任务，高阶任务进入「候差」，低阶任务继续；候差队列按品阶从高到低、截止时间排序；仙徒空闲时优先接高阶候差。超期通知功德殿，必要时由长老定夺中断低阶任务或转悬赏。
- 阵眼不持有重法宝（默认无 shell、无文件写权限）。

### R6 仙徒

- 仙徒在独立洞府中执行师门任务，向阵眼回禀，不直接与用户对话。
- V2.0 默认只读法宝；写操作、重启、外发必须经碧游宫客户端定夺。
- 每个仙徒有结界（法宝权限、文件范围、网络范围）。

### R7 巡阵

- 巡阵基于命灯与租约监督仙徒：超时、失联、卡死、孤儿清理、重派。
- 巡阵与灵脉共用观测数据，但巡阵负责恢复动作。
- 仙徒被杀后，师门任务可重派，状态不丢。

### R8 碧游宫客户端（功德殿 + 观星台）

- 碧游宫客户端是人的入口：提交目标、查看师门任务、因果线、仙徒状态、审批、验收道果。
- 功德殿是师门任务交接处（概念先定）：任务张贴、领命、交接、验收、记功德；V2.0-A 不实现后端，实现形态待后续讨论。
- 观星台是客户端内页：观测气机/因果线、查看待定夺任务。
- 首版可以只做只读 + 定夺，不做渠道管理、节点注册、Grafana 替代。

### R9 状态与产物

- 因果簿记录师门任务、派差、回禀、决策；藏经阁存道果、报告、证据。
- 功德入账以验收通过为准；交接、回禀、口头完成都不入账。
- 状态与算力分离：仙徒可替换，师门任务可恢复。
- 所有记录脱敏；符令不入日志。

### R10 兼容与边界

- 现有节点 `/v1/*`、阵图 `/zhentu/v1/*` 保持兼容。
- 仅内网；不接云端 Agent 服务；不对外公网暴露。
- 不直接照搬 dsh-superagent-prototype；只借鉴领域模型与运行时模式。

### R11 根骨、道行与任务品阶

- **根骨**：内门（PC）/ 外门（移动端），`root: inner | outer`；`quasheng` / `sanxian` 仅作兼容别名，不再作为规范称谓。
- 根骨决定能力上限与可用神通，不直接决定派差。
- **道行**：人仙、地仙、天仙、玄仙、金仙、太乙金仙、大罗金仙、准圣、混元。
- **任务品阶**：黄、玄、地、天、宇、宙、洪、荒；每阶有最低道行门槛，协议用 `task.tier: 1..8`。
- **风险**：清修（只读）、入世（有限写）、破阵（重启/变更）、传道（外发）。
- **派差**：先过硬门槛（道行、神通、法宝、授权），再按成功率、负载、时延、功德评分；高阶可接所有低阶任务，但只是资格，不是优先权；高阶不轻用。
- **成长**：完成师门任务积累功德；功德 + 成功率 + 道鉴 + 长老定夺决定晋升；仙箓与玉册即时更新。
- **悬赏**：无合格仙徒时任务进入悬赏，通知功德殿；不得降阶硬派。
- **护道**：洪阶/荒阶、破阵、传道任务的回禀需高阶仙徒或长老复核后才能结道果。

### R12 Token 成本、缓存与预算

- 每次模型调用记录：`ticket_id`、`thread_id`、`agent_id`、`step_id`、`model`、`provider`、`input_tokens`、`output_tokens`、`cache_hit_tokens`、`cache_miss_tokens`、`latency`、`currency`、`cost`。
- 价格表按 `provider + model` 配置缓存命中价、未命中价、输出价，带生效日期；外部模型按货币计价，本地模型按算力单位计价。
- 成本公式：`cost = hit × hit_price + miss × miss_price + output × output_price`；`cache_savings = hit × (miss_price - hit_price)`。
- 师门令必须带香火额度：`max_workers`、`max_input_tokens`、`max_output_tokens`、`max_cost`、`max_wall_time`。
- 预检按**冷缓存（0% 命中）**估算；运行中 80% 预警，100% 暂停并通知功德殿/观星台，不静默降级或继续。
- 缓存策略：稳定公共前缀（系统提示、法宝 schema、仙箓）在前，动态任务在后；并行前预热；同一 ticket 保持 provider affinity；注意 TTL；按内容哈希去重；限制 fan-out。
- NewAPI 必须保留或由仙徒侧补采 `cache_hit` / `cache_miss`；无法获取时标记 `cache_unknown`，不得按命中价估算。
- 任务报告展示：输入/输出 token、缓存命中率、香火、节省、预算使用率、按仙徒/步骤的成本拆分。
- 本地模型不是零成本：记录 token、并发占用、时延与能耗估算。

### R13 团队协作与任务板（参考 dsh Agent Teams）

- 一个师门任务/因果线可组一个**阵组**：阵眼为 Lead，仙徒为 teammate；默认关闭，复杂任务才开启。
- 任务板持久化 DAG：`pending` / `in_progress` / `completed` / `deleted`；支持 `blockedBy`、owner、CAS `expectedRevision`、`writeScopes`（仅提示不锁定）。
- 任务记录保持在模型历史之外；只向模型注入紧凑任务视图；任务结果追加在稳定前缀之后，避免破坏缓存。
- 任务变更不唤醒仙徒、不结束听候；需要行动必须显式传音。
- 上下文模式：**新生**（fresh，全新上下文）与**承法**（fork，继承已完成轮次）；按任务与缓存成本选择。
- 上限：`maxActiveSubagents`、`maxTasks`、fan-out、香火预算；超限拒绝，不排队占用。
- 分布式改造：任务板由阵图/因果簿承载；命灯租约、超时自动释放、增量投影；不依赖共享文件系统。

### R14 控制面高可用与降级（V2 不做全 P2P）

- 逻辑上仍是一个阵眼；物理上 2–3 个控制节点，leader election。
- 任务板复制/持久化；CAS + lease + fencing token；只有当前 leader 能派差。
- 仙徒自治：阵眼短暂不可用时，已领任务继续执行；新任务本地排队；恢复后对账。
- 幂等键与去重：同一师门任务不得因重连/重派重复执行。
- 脑裂防护：旧 leader 的派差被 fencing token 拒绝。
- 多站点/多域才引入分阵眼与总阵眼；全 P2P 非目标。

### R15 局域网开阵与入阵

- 协议基准：[docs/lan-formation-contract.md](../../../docs/lan-formation-contract.md)。
- 桌面端启动默认单机，不广播、不监听联阵；用户主动开阵后才成为阵主/阵眼。
- 开阵时选择「无密码（开放阵）」或「有密码（闭阵）」：开放阵无需阵符；闭阵需阵符；两者均无阵主确认。
- 移动端寻阵：通过 mDNS + UDP 广播发现局域网阵列表，显示阵名、阵主、版本、人数、是否加密、时延。
- 入阵：校验阵未满、协议兼容、阵未散；开放阵直接加入，闭阵校验阵符；通过即入阵，分配角色（默认外门仙徒）→ 下发仙箓与任务。
- 离阵/阵散：主动离阵或命灯熄灭；阵主退出即散阵，各端回单机，不崩溃、不丢本地数据。
- 安全：仅局域网接口；阵符 + 阵主确认；限速；不自动入阵；不上公网。
- V2 范围：桌面开阵 + Android 入阵；iOS 同步规划；桌面作为 guest 入阵可后置。

## 第一个垂直切片（建议）

**灵脉警讯处置**：

```text
灵脉 P1/P2 警讯（知客堂）
  → 门规 Gate：仙徒白名单 + 级别
  → 观星：是否值得处理
  → 师门任务：诊断仙徒异常（地阶 / 清修）
  → 师门令：只读法宝（气机/道录），禁止重启
  → 派差：内门仙徒（道行 ≥ 天仙）
  → 回禀：根因 + 建议动作
  → 功德殿/观星台：人工定夺后再执行修复
```

选择理由：主动、风险低、复用现有灵脉与内门仙徒；能同时验证知客堂、阵眼、仙徒、师门令、巡阵与碧游宫客户端。

## Non-goals

- ❌ 不做通用 Agent 平台、公网服务、云端 Agent 接入。
- ❌ 不做无条件写操作或全自动修复；V2.0 保留人工定夺。
- ❌ 不要求外门仙徒具备完整法宝与运行环境。
- ❌ 不在本任务内重写 V1.0 部署与节点契约。
- ❌ 不在本任务内实现完整碧游宫客户端 UI 改版。
- ❌ 不在本任务内实现功德殿后端/独立服务；先定概念与功德入账规则。
- ❌ 不做全 P2P：V2 保留一个逻辑阵眼，只做控制面高可用与仙徒自治。

## Open Decisions

1. 第一个知客堂信源是否选「灵脉警讯处置」。
2. 阵眼放在中枢机还是仙徒节点；使用轻量模型还是较强模型。
3. 仙徒法宝权限：V2.0 是否先只读。
4. dsh 是只做碧游宫客户端 UI，还是也作为仙徒运行时。
6. 道行九境是否采用，还是先精简为六境。
7. 是否在后续版本重命名 `nodes/quasheng` / `nodes/sanxian` 目录，还是永久保留为兼容名。
8. 任务品阶与风险四档是否按本 PRD 执行。
9. 功德殿实现形态（客户端页面 / 阵图接口 / 独立服务）待后续讨论。
10. 价格表来源、货币与本地模型算力单位（token / GPU 秒 / 能耗）待定。
11. 并行预热策略：单请求预热、错峰 fan-out，还是接受冷启动首次全 miss。
