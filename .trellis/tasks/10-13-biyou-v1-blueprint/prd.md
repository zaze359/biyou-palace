## 〇、产物定义（2026-11-21 修订）

> 本节优先于后文旧的集群验收口径。

- **唯一交付物是两条客户端产品线**：桌面客户端（macOS / Windows）与移动端（Android 先行，iOS 同步规划）。
- **默认单机自闭环**；联阵是可选加法，不是前提。
- **桌面端启动默认单机，不自动开阵**；用户主动开阵后才担任阵眼。移动端默认单机，入阵后作为外门仙徒。
- **联阵方式**：局域网「开阵 / 寻阵 / 入阵」，类似魔兽争霸 III 的 LAN 房间列表；无云大厅、无账号、无公网。
- **服务端不是独立交付物**；旧集群部署降级为联阵后端 / 参考实现。
- **验收口径**改为：桌面单机完整闭环、移动端轻任务闭环、两端可局域网联阵。

## 一、目标与价值（Goal & User Value）

- **项目全称**：BiYouPalace 碧游宫 · 异构万仙推理集群｜**仓库**：biyou-palace
- **Slogan**：不问根骨，万仙入阵；同参大道，内网演道
- **价值**：复用闲置 PC 与安卓旧机，基于 NewAPI + Ollama 构建一套**内网闭环**的异构 AI 推理集群，提供统一 OpenAI 兼容接口、加权负载均衡、复杂任务编排、节点监控与自动化性能检定。让零散闲置算力在内网组成可调度、可观测、可自检的推理阵列，数据不出局域网。

## 二、已确认事实（Confirmed Facts）

- **技术栈已定**：碧游宫=NewAPI(Docker)；算力=准圣 Ollama(PC x86) + 散仙 smallphone 派生 llama.cpp 原生安卓 App(ARM)；阵图=Python+FastAPI+LangGraph；监控=Prometheus+Grafana+node-exporter+自定义采集；检定=Python+httpx+vegeta/k6；编排=Docker/Docker Compose。
- **规模**：十几台闲置终端的**小型**万仙阵，非上百节点。
- **网络边界**：仅内网，数据不出「金鳌岛局域网」，不对外公网暴露。
- **不做分布式张量并行**：仅**任务级**分布式（子任务分发），不做大模型单卡拆分。
- **不改 Ollama 源码**：完全基于原版，不修改 Ollama 本身；散仙节点经决策改用 smallphone 的 llama.cpp 原生 App（已接受的运行时分叉），准圣仍严格守 Ollama。
- **运行时异构（已决策）**：准圣 = Ollama（PC，7B/14B）；散仙 = smallphone 派生的 llama.cpp 原生安卓 App（轻量，非 Ollama）。两者经碧游宫 / 阵图统一调度；散仙需包一层 OpenAI 兼容本地服务以作为 NewAPI 渠道。
- **五大模块**：A 碧游宫中枢 / B 阵图编排 / C 仙徒节点集群 / D 灵脉监控 / E 道鉴检定。
- **五大阶段**：① 立坛筑基 ② 布下万仙阵 ③ 阵图显化 ④ 守阵试炼 ⑤ 归档传道。

## 三、需求（Requirements）

### 模块 A · 碧游宫中枢（NewAPI 网关）
渠道管理、负载均衡、心跳探测、故障隔离、令牌统计、鉴权；提供统一 OpenAI 兼容接口，支持加权负载均衡、按模型路由。

### 模块 B · 阵图 ZhenTu 编排服务
请求解析、任务拆解、并行子任务调度、结果合并、异常重试、降级策略；对外暴露统一 API 接收「求道指令」，自动拆为多个独立子任务并行调用碧游宫网关，再合并润色输出道果。

### 模块 C · 仙徒节点集群（异构算力单元：Ollama + llama.cpp）
- 准圣节点（PC 有线 · Ollama）：7B/14B 量化大模型，主 LLM 推演。
- 散仙节点（安卓 llama.cpp App · 非 Ollama）：轻量模型，承担 Embedding、OCR、文本分类。
- 节点均为**自治双模单元**：本地推理对外暴露 OpenAI 兼容服务 + 本地独立对话 / 调外部模型自用。
- 节点支持动态注册、心跳上报、故障自动剔除。

### 模块 D · 灵脉 LingMai 监控系统
采集节点状态、硬件温度、内存、Ollama 指标，存储时序数据，Grafana 看板（仙侠指标命名）。

### 模块 E · 道鉴 DaoJian 检定工具集
自动化压测脚本，单节点修为检定 + 集群合阵压测，生成 Markdown 测试报告。

### 阶段里程碑（节奏已调整 · 自底向上：先节点后协调）

## 六、风险预案

- 散仙 WiFi 不稳、高温降频 → 温度超标记降权 + 阵图超时重试 + 仅分轻量任务。
- 阵图编排复杂度高、子任务依赖易错 → 先固定场景任务流，逐步扩展动态拆分；加详细链路日志。
- NewAPI 心跳探测延迟、故障感知慢 → 调小心跳周期 + 阵图层独立超时双重防护。
- 老旧设备内存不足、Ollama OOM → 低量化 GGUF + Ollama 自动重启 + 内存告警。

## 七、延后决策（Deferred · 非阻塞，轮到对应阶段再定）

- **阶段三编排选型**：LangGraph 是否最终采用，还是先用轻量 DAG / 手写调度降低复杂度（蓝图已写 LangGraph，属阶段三前可复核的技术决策）。
- **压测工具取舍**：vegeta vs k6，二者皆备还是二选一（影响模块 E 检定工具实现）。
- **散仙节点运行时与实现语言（已决策：采用 smallphone / llama.cpp）**：分层原则已确认（共享基类 + 准圣 / 散仙独立实现 + 阵图路由前置判定，禁止 if/else 混写）。已查旧项目 `smallphone`：KMP+Compose 安卓 App，直接集成 llama.cpp（JNI，非 Ollama），目标 Android+iOS（无桌面 target），本身是聊天 App。**决策：散仙节点采用 smallphone 派生的 llama.cpp 原生安卓 App**，复用其 JNI 桥 / 引擎 / 模型下载；配套动作：① 移除 iOS target（BiYouPalace 仅需安卓）；② 剥离聊天 UI，补节点智能体层（心跳上报灵脉、向碧游宫注册、接收子任务）；③ 包一层 OpenAI 兼容本地 HTTP 服务（如 Ktor）将既有本地推理暴露给集群（同时保留节点独立对话能力），作为 NewAPI 渠道接入碧游宫。代价：运行时与准圣（Ollama）分叉、引入 Kotlin/Gradle/NDK/CMake + 巨型 llama.cpp 工具链；准圣 / 散仙 调度逻辑仍落在阵图（Python）路由层。影响：`nodes/sanxian` 现为 KMP 模块，仓库新增 Kotlin 工程。

## 九、整体架构与部署拓扑（规划已锁定）

### 架构模型
采用**中心化调度 + 分布式执行**的混合体系（非完全去中心化 P2P，非模型张量并行），与「万仙阵」同构：
- **任务级分布式**：复杂求道指令拆为独立子任务，分发至异构算力节点并行推演，由碧游宫网关 + 阵图编排统一调度，聚合为道果。
- **万仙阵类比映射**：通天教主 / 阵眼 = 碧游宫网关（全局统筹）；仙徒 = 自治、修为异构的执行单元；太极 / 两仪 / 四象子阵 = 阵图编排的子任务分组。
- **仙徒节点为自治双模单元**：每个仙徒（准圣 PC / 散仙手机）既是可独立使用的个体——本地跑模型并向集群暴露 OpenAI 兼容服务（供碧游宫调度），也可本地独立对话 / 调用外部模型自用；用户既可经统一网关（碧游宫 / 阵图）发起复杂求道，也可直连任一仙徒节点对话。散仙（smallphone）天然具备此形态（自带聊天客户端 + 本地 llama.cpp 推理）。
- **容错边界**：单个仙徒退场 → 大阵可继续（网关自动剔除 + 阵图重试降级）；主控阵眼（中枢机 / 网关）失效 → 全阵溃散。

### 部署拓扑（星型）
- **中枢机（一台常开 PC）**：Docker Compose 集中运行 碧游宫(NewAPI+DB)、阵图(ZhenTu)、灵脉(Prometheus+Grafana)；道鉴按需在此运行。
- **边缘仙徒节点（准圣 = 其余 PC，散仙 = 安卓手机）**：准圣仅运行 Ollama + 灵脉采集器（7B/14B）；散仙运行 smallphone 派生的 llama.cpp 原生 App + 灵脉采集器（轻量）。两运行时分叉，散仙经 OpenAI 兼容本地服务接入碧游宫。

## 十、V2.0 主叙事升级：Super-agent 架构（2026-11-21 确认）

### 10.1 决策

项目不再只定义为「异构推理集群」，而是：

> **一个持续在线、事件驱动、能统领异构仙徒 Agent 干活并验收的内网 Super-agent 系统。**

- **V1.0 = 执行底座**：山门、内门/外门仙徒、阵图、灵脉、道鉴全部保留，不回退。
- **V2.0 = Super-agent 层**：阵眼 / 仙徒、知客堂 / 缘起、师门任务 / 师门令、巡阵、碧游宫客户端（功德殿 + 观星台）。
- 现有 `/v1/*` 节点契约与阵图既有接口保持向后兼容；V2.0 以新增契约为主。
- 新任务入口：`11-21-biyou-superagent`。
- **命名基准**：[docs/naming.md](../../../docs/naming.md)。碧游宫 = 道门/系统总称；山门 = NewAPI 网关；仙徒 = Worker；阵眼 = Router；碧游宫客户端 = Client；功德殿 = Task Hall；观星台 = 客户端内观测/定夺页；师门任务 = Ticket；师门令 = Mandate；知客堂 = Source；缘起 = Trigger。

### 10.2 四个基础特征

| Super-agent 特征 | 碧游宫落点 |
|---|---|
| **连续** | 碧游宫客户端、灵脉、IM/邮件等入口共享同一套全局上下文；用户始终面对同一个「碧游宫」 |
| **高效** | 阵眼只协调分派，仙徒并行执行；不要求一个会话串行干完所有事 |
| **主动** | 灵脉警讯、仙徒异常、定时值守、群聊反馈都可成为缘起 |
| **持久** | 任务状态与算力分离；仙徒掉线可重派，异常由巡阵恢复 |

### 10.3 五个支撑模块

| Super-agent 模块 | 碧游宫落点 |
|---|---|
| 阵眼 / 仙徒双层 | 阵眼 = 常驻主持（全局上下文、只分派）；仙徒 = 执行门人（隔离洞府、独立工作目录、并行执行） |
| 事件驱动 | 知客堂 = 碧游宫客户端目标 / 灵脉警讯 / 定时值守 / IM；缘起 = 一条待研判事件 |
| 面向人的交互 | 碧游宫客户端：师门任务、审批、验收、纠偏；功德殿负责任务交接 |
| 计算 / 状态 / 环境分离 | 算力在仙徒；因果簿与道果在阵图/藏经阁；每个仙徒独立洞府 |
| 巡阵 | 灵脉 + 阵图 supervisor：命灯、租约、超时、重派、孤儿清理 |

### 10.4 领域模型

| Super-agent 概念 | 碧游宫命名建议 | 职责 |
|---|---|---|
| 知客堂（Source） | 信源 | 道门接事入口，保存读取位置与身份 |
| 缘起（Trigger） | 触发 | 一条不可变事件，幂等与审计单位 |
| 因果线（Thread） | 因果线 | 同一任务/话题下的事件流 |
| 观星（Eval） | 研判 | 判断是否立项；程序 Gate + 模型 Assessment |
| 师门任务（Ticket） | 道门差事 / 工单 | 被授权的工作单元；只有观星能创建 |
| 师门令（Mandate） | 师门令 / 授权 | 范围、期限、强度、可用法宝、数据边界；不可变 |
| 派差（Assignment） | 派差 | 师门任务与某个仙徒实例的绑定 |
| 仙徒（Worker） | 门人 / 执行单元 | 隔离洞府中执行任务，向阵眼回禀，不直接对用户 |
| 回禀（Report） | 回禀 | progress / waiting / ready / blocked / failed / dropped |
| 传音（Channel） | 传音 | 回复到原入口 |
| 因果订阅（Subscription） | 因果订阅 | 后续缘起直达对应仙徒，不再经阵眼 |
| 巡阵（Watchdog） | 巡阵 | 命灯、租约、超时、重派、异常恢复 |

### 10.5 目标架构

```text
知客堂 Source（碧游宫客户端目标 / 灵脉警讯 / 定时值守 / IM）
        │ 缘起 Trigger
        ▼
阵眼 Router（常驻主持）
  ├─ Gate：门规准入（谁、来源、级别）
  ├─ 观星 Eval：模型级研判（是否立项）
  ├─ 师门任务 + 师门令：道门差事与授权
  ├─ 派差 Assignment：交给合适仙徒
  └─ 全局神识 / 对外回禀
        │
        ▼
仙徒 Worker（异构）
  ├─ 内门仙徒：Ollama + 法宝 + 文件
  ├─ 外门仙徒：llama.cpp + OCR/Embedding/分类
  └─ 独立洞府 / 工作目录 / 回禀
        │
        ▼
山门 NewAPI（模型面）
        │
        ▼
巡阵 Watchdog（命灯 / 租约 / 超时 / 重派）
```

关键分工：

- **山门 NewAPI 只做模型面**，不承担任务编排；
- **阵图升级为阵眼 + 调度面**，负责任务而不是模型请求；
- **dsh 只做仙徒运行时 / 碧游宫客户端 UI 参考**，不做集群调度器；
- **碧游宫客户端** 是人的入口，不是新的编排中心；功德殿负责任务交接。

### 10.7 第一个垂直切片（建议）

**灵脉告警处置**：

```text
灵脉 P1/P2 警讯（知客堂）
  → Gate：仙徒白名单 + 级别（门规）
  → 观星：是否值得处理
  → 师门任务：诊断仙徒异常（地阶 / 清修）
```

### 10.11 根骨、道行与任务品阶（2026-11-21 补充）

**根骨与道行分离**：

- **根骨** = 先天形态：内门（PC + Ollama）/ 外门（安卓 + llama.cpp）。
- **道行** = 后天修为：人仙 → 地仙 → 天仙 → 玄仙 → 金仙 → 太乙金仙 → 大罗金仙 → 准圣 → 混元。
- 派差看道行、神通与授权，不直接看根骨；根骨只决定上限与可用神通。
- V1.0 的「准圣 / 散仙」是节点名（根骨），现退役；新文档统一用「内门 / 外门」，代码 `quasheng` / `sanxian` 仅作兼容别名。

**任务品阶与风险**：

| 品阶 | 最低道行 | 典型任务 |
|---|---|---|
| 黄阶 | 人仙 | 问答、分类、OCR、Embedding |
| 玄阶 | 地仙 | 摘要、翻译、单步法宝 |
| 地阶 | 天仙 | 多步诊断、文档审查 |
| 天阶 | 玄仙 | 复杂诊断、跨文档推理、有限写 |
| 宇阶 | 金仙 | 跨系统分析、代码/运维复杂任务 |
| 宙阶 | 太乙金仙 | 长链路任务、高难推理、复核 |
| 洪阶 | 大罗金仙 | 专家级任务、全局复盘、跨域协调 |
| 荒阶 | 准圣 | 宗门级决策、最高风险/最高难度，需掌门/长老定夺 |

> 品阶取「天地玄黄，宇宙洪荒」，由低到高：**黄 → 玄 → 地 → 天 → 宇 → 宙 → 洪 → 荒**；协议用 `task.tier: 1..8`。

| 风险 | 含义 | 授权 |
|---|---|---|
| 清修 | 只读 | 师门令 + 只读法宝 |
| 入世 | 有限写、可回滚 | 师门令 + 定夺 |
| 破阵 | 重启/变更服务 | 师门令 + 护道 + 定夺 |
| 传道 | 外发/对外通信 | 师门令 + 定夺 |

**派差硬规则**：

1. 不越阶：仙徒道行 ≥ 师门任务最低道行。
2. 可低接：高阶仙徒可接所有低阶任务；但「可接」只是资格，不是优先权。
3. 不越权：风险必须在师门令授权内；破阵/传道必须定夺。
4. 高阶不轻用：低阶任务优先给刚好够用的仙徒。
5. 无可用则悬赏：不得静默降阶派给低阶仙徒。
6. 动态道行：晋升/降阶后仙箓与玉册即时生效。
7. 护道复核：洪阶/荒阶、破阵、传道任务的回禀需高阶仙徒或长老复核。
8. 不抢占（V2）：高阶任务到达、高阶仙徒正执行低阶任务时，高阶任务进入「候差」，低阶任务继续；候差队列按品阶从高到低、截止时间排序；仙徒空闲时优先接高阶候差。超期通知功德殿，必要时由长老定夺中断低阶任务或转悬赏。

**道行精进**：

- 完成师门任务积累功德；功德 + 成功率 + 道鉴 + 长老定夺决定晋升。
- 功德入账以验收通过为准；交接、回禀、口头完成都不入账。
- 晋升后更新仙箓、可接品阶、神通、法宝与限额；玉册立即刷新。
- 根骨设定上限，道行决定当前能接什么；这就是「不问根骨」。

### 10.12 Token 成本、缓存与预算（2026-11-21 补充）

多 Agent 会把 token 消耗放大，成本必须作为一等指标：

- **逐次记账**：每次模型调用记录师门任务、仙徒、步骤、模型、provider、输入/输出 token、缓存命中/未命中 token、时延与费用。
- **分开计价**：价格表按 `provider + model` 配置缓存命中价、未命中价、输出价；外部模型按货币，本地模型按算力单位。
- **预检冷缓存**：并行 fan-out 前按 0% 命中估算；运行中 80% 预警，100% 暂停并通知功德殿/观星台。
- **缓存策略**：稳定公共前缀在前、动态任务在后；并行前预热；同一任务保持 provider affinity；注意 TTL；按内容哈希去重；限制 fan-out。
- **任务报告**：展示 token、缓存命中率、香火、节省、预算使用率，以及按仙徒/步骤的拆分。
- **概念区分**：香火是消耗，功德是贡献；本地模型不是零成本。
- **无法获取缓存字段**时标记 `cache_unknown`，不得按命中价估算。

### 10.13 团队协作与任务板（参考 dsh Agent Teams，2026-11-21 补充）

DeepSeek 的 Agent Teams 不是“多 Agent 自由对话”，而是“Lead + subagent 树 + 持久共享任务板”。可借鉴的核心：

- **阵组**：一个师门任务/因果线一个协作组；阵眼为 Lead，仙徒为 teammate；默认关闭。
- **任务板**：持久 DAG，支持 owner、`blockedBy`、CAS revision、`writeScopes`（仅提示不锁定）。
- **上下文克制**：任务记录在模型历史之外，只注入紧凑任务视图；任务结果追加在稳定前缀之后，保护 KV cache。
- **显式传音**：任务变更不唤醒仙徒；需要行动必须 `send_message`，避免无谓 token。
- **新生/承法**：fresh 全新上下文，fork 继承已完成轮次；按任务与缓存成本选择。
- **上限**：`maxActiveSubagents`、`maxTasks`、fan-out、香火预算；超限拒绝，不排队占用。
- **分布式改造**：dsh 是单进程共享文件系统；碧游宫必须把任务板放到阵图/因果簿，用命灯租约、超时释放、增量投影替代共享 FS。

### 10.14 去中心化评估（2026-11-21）

结论：**执行层已经去中心化；V2 不做全 P2P，控制面做高可用，保留一个逻辑阵眼；多站点再走联邦阵眼。**

| 层级 | 形态 | 适用 | 判断 |
|---|---|---|---|
| L0 | 中心调度 + 分布执行（当前） | 单内网、十几台 | 简单，但阵眼是单点 |
| L1 | 控制面高可用：2–3 控制节点、leader election、任务板复制、租约/fencing | V2 推荐 | 保留全局规划/预算/缓存亲和，消除单点 |
| L2 | 联邦阵眼：每域一个分阵眼，总阵眼只做跨域协调 | 多站点/多归属 | V3 再考虑 |
| L3 | 全 P2P：CRDT/gossip 任务板、无全局调度 | 无中心、信任less | 不推荐 |

理由：

- 十几台内网规模下，全局规划、香火预算、缓存亲和、审计都需要一个逻辑协调者；全 P2P 收益低、复杂度和排障成本高。
- 真正的单点是**控制面与状态**，不是执行层；先做 L1 即可。
- 仙徒自治：阵眼短暂不可用时，已领任务继续，新任务本地排队，恢复后对账。
- 脑裂防护：CAS + lease + fencing token；只有当前 leader 能派差。
- 多站点/多归属时才引入「分阵眼 / 总阵眼」，不要在单内网提前复杂化。

### 10.15 局域网开阵与入阵（2026-11-21）

- **协议基准**：[docs/lan-formation-contract.md](../../../docs/lan-formation-contract.md)。
- **启动默认**：桌面端单机模式，本地阵眼只服务本机，不广播、不监听联阵；用户主动开阵后才成为阵主/阵眼。
- **开阵**：选择「无密码（开放阵）」或「有密码（闭阵）」，并声明阵名、容量、可见性。
- **开放阵**：同局域网可见，入阵无需阵符；校验通过即加入，无需阵主确认；阵主可踢人。
- **闭阵**：入阵需阵符；阵符校验通过即加入，无需阵主确认；阵主可踢人。
- **寻阵**：移动端/其他桌面端通过 mDNS + UDP 广播发现局域网阵列表，显示阵名、阵主、版本、人数、是否加密、时延。
- **入阵**：校验阵未满、协议兼容、阵未散；开放阵直接加入，闭阵校验阵符；通过即入阵，分配角色（默认外门仙徒）→ 下发仙箓与任务。
- **离阵**：仙徒主动离阵或命灯熄灭；阵主回收租约、重派任务。
- **阵散**：阵主退出即散阵；各端回单机模式，不崩溃、不丢本地数据。
- **安全**：仅局域网接口；开放阵仅限可信内网；闭阵靠阵符校验；限速；不自动入阵；不上公网；阵主可踢人。
- **V2 范围**：桌面开阵 + Android 入阵；iOS 同步规划；桌面作为 guest 入阵可后置。
