# PRD · BiYouPalace 碧游宫 V1.0 主规划

> 规划形态：本文件为**单一主规划文档**（按用户决策，不拆阶段子任务、不单独写 design.md / implement.md）。
> 五大阶段以章节形式保留；阶段一~五的细化设计将在后续单独立项时展开。
> 来源：用户提供的《BiYouPalace 碧游宫 开发蓝图》。

## 一、目标与价值（Goal & User Value）

- **项目全称**：BiYouPalace 碧游宫 · 异构万仙推理集群｜**仓库**：biyou-palace
- **Slogan**：不问根骨，万仙入阵；同参大道，内网演道
- **价值**：复用闲置 PC 与安卓旧机，基于 NewAPI + Ollama 构建一套**内网闭环**的异构 AI 推理集群，提供统一 OpenAI 兼容接口、加权负载均衡、复杂任务编排、节点监控与自动化性能检定。让零散闲置算力在内网组成可调度、可观测、可自检的推理阵列，数据不出局域网。

**命名约定（贯穿全链路，不得混用现世/仙侠词）**

| 现世概念 | 仙侠命名 |

| NewAPI 网关 | 碧游宫（中枢） |
| 编排服务 | 阵图 ZhenTu |
| PC 主力节点 | 准圣节点 |
| 安卓 llama.cpp 节点 | 散仙节点 |
| 监控系统 | 灵脉 LingMai |
| 结果聚合 | 道果 DaoGuo |

## 二、已确认事实（Confirmed Facts）

- **技术栈已定**：碧游宫=NewAPI(Docker)；算力=准圣 Ollama(PC x86) + 散仙 smallphone 派生 llama.cpp 原生安卓 App(ARM)；阵图=Python+FastAPI+LangGraph；监控=Prometheus+Grafana+node-exporter+自定义采集；检定=Python+httpx+vegeta/k6；编排=Docker/Docker Compose。
- **规模**：十几台闲置终端的**小型**万仙阵，非上百节点。
- **网络边界**：仅内网，数据不出「金鳌岛局域网」，不对外公网暴露。
- **不做分布式张量并行**：仅**任务级**分布式（子任务分发），不做大模型单卡拆分。
- **不改 Ollama 源码**：完全基于原版，不修改 Ollama 本身；散仙节点经决策改用 smallphone 的 llama.cpp 原生 App（已接受的运行时分叉），准圣仍严格守 Ollama。
- **运行时异构（已决策）**：准圣 = Ollama（PC，7B/14B）；散仙 = smallphone 派生的 llama.cpp 原生安卓 App（轻量，非 Ollama）。两者经碧游宫 / 阵图统一调度；散仙需包一层 OpenAI 兼容本地服务以作为 NewAPI 渠道。
- **五大模块**：A 碧游宫中枢 / B 阵图编排 / C 仙徒节点集群 / D 灵脉监控 / E 道鉴检定。
- **五大阶段**：① 立坛筑基 ② 布下万仙阵 ③ 阵图显化 ④ 守阵试炼 ⑤ 归档传道。

## 三、需求（Requirements）

### 模块 A · 碧游宫中枢（NewAPI 网关）
渠道管理、负载均衡、心跳探测、故障隔离、令牌统计、鉴权；提供统一 OpenAI 兼容接口，支持加权负载均衡、按模型路由。

### 模块 B · 阵图 ZhenTu 编排服务
请求解析、任务拆解、并行子任务调度、结果合并、异常重试、降级策略；对外暴露统一 API 接收「求道指令」，自动拆为多个独立子任务并行调用碧游宫网关，再合并润色输出道果。

### 模块 C · 仙徒节点集群（异构算力单元：Ollama + llama.cpp）
- 准圣节点（PC 有线 · Ollama）：7B/14B 量化大模型，主 LLM 推演。
- 散仙节点（安卓 llama.cpp App · 非 Ollama）：轻量模型，承担 Embedding、OCR、文本分类。
- 节点均为**自治双模单元**：本地推理对外暴露 OpenAI 兼容服务 + 本地独立对话 / 调外部模型自用。
- 节点支持动态注册、心跳上报、故障自动剔除。

### 模块 D · 灵脉 LingMai 监控系统
采集节点状态、硬件温度、内存、Ollama 指标，存储时序数据，Grafana 看板（仙侠指标命名）。

### 模块 E · 道鉴 DaoJian 检定工具集
自动化压测脚本，单节点修为检定 + 集群合阵压测，生成 Markdown 测试报告。

### 阶段里程碑（节奏已调整 · 自底向上：先节点后协调）

> 蓝图原五阶段顺序已调整：**先将两个仙徒节点智能体各自实现为独立可用的自治单元**，再逐步叠加网关接入 → 编排聚合 → 监控检定 → 文档部署。原五阶段目标保留为各步骤的验收细则。

1. **第一步 · 仙徒智能体各自成型**（原「立坛筑基」的节点部分）
   分别实现准圣（PC）与散仙（安卓）两套节点智能体，各自成为**独立可用的自治双模单元**：
   - 准圣：PC + Ollama（7B/14B）+ Python 节点智能体。
   - 散仙：安卓 App（smallphone 派生，llama.cpp）+ KMP 节点智能体（去 iOS target、保留本地对话能力、补 Ktor 的 OpenAI 兼容服务；聊天作为本地自用模式并存）。
   - 每个智能体须具备：① 本地推理并对外暴露 **OpenAI 兼容推理服务**；② **本地独立对话 / 调外部模型**自用；③ 最简 **健康 / 能力端点**（返回机型、可用模型、负载等），供后续网关探活、灵脉采集、阵图路由消费——**本步不含完整灵脉**。
   - 验收：任一节点单独运行即可本地对话并对外提供 OpenAI 兼容推理；健康端点返回能力信息；**此时尚未接入集群**。

   > **协议契约**：详见 `docs/node-agent-contract.md`（v1.0）。两类节点共用同一套 HTTP 契约（`GET /v1/health`、`GET /v1/models`、`POST /v1/chat/completions`、`POST /v1/embeddings`），本地客户端通过 localhost 复用同一套端点；以**协议共享取代 KMP 代码共享**，并以能力声明驱动上层路由。

2. **第二步 · 碧游宫网关接入**（原「立坛筑基」网关部分 + 「布下万仙阵」）
   Docker 部署 NewAPI，将各仙徒作为渠道纳入，打通统一 OpenAI 入口与基础转发；配置权重、心跳、超时、故障自动隔离；两类调度模式验证（同模型多副本分摊 / 按模型路由）；基础并发压测。
   - 验收：网关可转发至任意仙徒；压测按权重分配；手动关停节点后网关自动隔离。

3. **第三步 · 阵图编排 + 道果聚合**（原「阵图显化」）
   阵图 ZhenTu 服务：请求解析 / 任务拆解、并行子任务调度、结果（道果）合并润色、异常重试与降级；示例场景（图→OCR+Embedding+LLM 综合回答）。
   - 验收：复杂请求自动拆多子任务并行；单散仙掉线不中断整条推演。

4. **第四步 · 灵脉监控 + 道鉴检定**（原「守阵试炼」）
   灵脉：分运行时采集器（准圣采 Ollama 指标 / 散仙采 llama.cpp 指标）+ Prometheus + Grafana 看板（仙侠命名）+ 告警规则。道鉴：压测与 Markdown 报告。故障注入与长时耐久。
   - 验收：看板实时可见全仙徒状态；故障自动隔离；长时运行不雪崩；检定报告输出。

5. **第五步 · 归档传道**（原「归档传道」）
   全套文档、一键部署（Docker Compose）、运维脚本（批量注册 / 日志收集 / 批量检定）、已知限制与迭代路线。
   - 验收：他人依文档从零复现整套集群。

## 四、验收标准（Acceptance Criteria · V1.0 整体）

- [ ] 异构 PC + 安卓节点全部接入内网，Ollama 正常提供推理。
- [ ] 碧游宫网关支持负载均衡、故障节点自动隔离。
- [ ] 阵图编排可拆解复杂请求，多仙徒并行演算、合并道果，支持部分节点降级。
- [ ] 灵脉看板实时监控所有仙徒修为、温度、链路状态。
- [ ] 道鉴工具能够自动化检定，输出完整集群性能报告。
- [ ] 全部推演流程在内网，数据不出金鳌岛。

## 五、非目标 / 边界（Out of Scope）

- ❌ 不做模型分布式张量并行（仅任务级分布式）。
- ❌ 不对外公网暴露集群，仅内网使用。
- ❌ 不开发 / 修改 Ollama 底层，完全基于原版（注：准圣严格守 Ollama；散仙经决策改用 smallphone 的 llama.cpp 原生 App，属已接受的运行时分叉，不修改 Ollama 本身）。
- ❌ 不支持大规模上百节点（目标为十几台小型万仙阵）。
- ❌ V1.1 后续方向（自动入阵、动态权重、任务优先级、日志审计）不纳入本期。
- ⚠️ 中枢机 / 碧游宫网关为**单点**（阵眼失效则全阵不可用）—— V1.0 已知限制，高可用分布列入 V1.1。

## 六、风险预案

- 散仙 WiFi 不稳、高温降频 → 温度超标记降权 + 阵图超时重试 + 仅分轻量任务。
- 阵图编排复杂度高、子任务依赖易错 → 先固定场景任务流，逐步扩展动态拆分；加详细链路日志。
- NewAPI 心跳探测延迟、故障感知慢 → 调小心跳周期 + 阵图层独立超时双重防护。
- 老旧设备内存不足、Ollama OOM → 低量化 GGUF + Ollama 自动重启 + 内存告警。

## 七、延后决策（Deferred · 非阻塞，轮到对应阶段再定）

- **阶段三编排选型**：LangGraph 是否最终采用，还是先用轻量 DAG / 手写调度降低复杂度（蓝图已写 LangGraph，属阶段三前可复核的技术决策）。
- **压测工具取舍**：vegeta vs k6，二者皆备还是二选一（影响模块 E 检定工具实现）。
- **散仙节点运行时与实现语言（已决策：采用 smallphone / llama.cpp）**：分层原则已确认（共享基类 + 准圣 / 散仙独立实现 + 阵图路由前置判定，禁止 if/else 混写）。已查旧项目 `smallphone`：KMP+Compose 安卓 App，直接集成 llama.cpp（JNI，非 Ollama），目标 Android+iOS（无桌面 target），本身是聊天 App。**决策：散仙节点采用 smallphone 派生的 llama.cpp 原生安卓 App**，复用其 JNI 桥 / 引擎 / 模型下载；配套动作：① 移除 iOS target（BiYouPalace 仅需安卓）；② 剥离聊天 UI，补节点智能体层（心跳上报灵脉、向碧游宫注册、接收子任务）；③ 包一层 OpenAI 兼容本地 HTTP 服务（如 Ktor）将既有本地推理暴露给集群（同时保留节点独立对话能力），作为 NewAPI 渠道接入碧游宫。代价：运行时与准圣（Ollama）分叉、引入 Kotlin/Gradle/NDK/CMake + 巨型 llama.cpp 工具链；准圣 / 散仙 调度逻辑仍落在阵图（Python）路由层。影响：`nodes/sanxian` 现为 KMP 模块，仓库新增 Kotlin 工程。

## 八、后续迭代路线（V1.1，本期不做）

自动入阵（新节点上线自动注册）、动态权重（灵脉实时性能调权）、任务优先级、日志审计（每道果溯源协同仙徒）。

## 九、整体架构与部署拓扑（规划已锁定）

### 架构模型
采用**中心化调度 + 分布式执行**的混合体系（非完全去中心化 P2P，非模型张量并行），与「万仙阵」同构：
- **任务级分布式**：复杂求道指令拆为独立子任务，分发至异构算力节点并行推演，由碧游宫网关 + 阵图编排统一调度，聚合为道果。
- **万仙阵类比映射**：通天教主 / 阵眼 = 碧游宫网关（全局统筹）；仙徒 = 自治、修为异构的执行单元；太极 / 两仪 / 四象子阵 = 阵图编排的子任务分组。
- **仙徒节点为自治双模单元**：每个仙徒（准圣 PC / 散仙手机）既是可独立使用的个体——本地跑模型并向集群暴露 OpenAI 兼容服务（供碧游宫调度），也可本地独立对话 / 调用外部模型自用；用户既可经统一网关（碧游宫 / 阵图）发起复杂求道，也可直连任一仙徒节点对话。散仙（smallphone）天然具备此形态（自带聊天客户端 + 本地 llama.cpp 推理）。
- **容错边界**：单个仙徒退场 → 大阵可继续（网关自动剔除 + 阵图重试降级）；主控阵眼（中枢机 / 网关）失效 → 全阵溃散。

### 部署拓扑（星型）
- **中枢机（一台常开 PC）**：Docker Compose 集中运行 碧游宫(NewAPI+DB)、阵图(ZhenTu)、灵脉(Prometheus+Grafana)；道鉴按需在此运行。
- **边缘仙徒节点（准圣 = 其余 PC，散仙 = 安卓手机）**：准圣仅运行 Ollama + 灵脉采集器（7B/14B）；散仙运行 smallphone 派生的 llama.cpp 原生 App + 灵脉采集器（轻量）。两运行时分叉，散仙经 OpenAI 兼容本地服务接入碧游宫。

### 单点风险（已知限制）
碧游宫网关 / 中枢机为单点（阵眼失效则阵法溃散）。V1.0 小型内网规模下可接受，高可用 / 分布列入 V1.1。
