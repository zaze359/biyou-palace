# 碧游宫命名规范（洪荒体系）

> 版本：v2.1 · 2026-11-21（免确认入阵与校验规则）
> 适用范围：产品叙事、文档、UI、日志、任务与契约说明。
> 代码标识符、API 字段、配置键仍使用英文，不因本规范改名。
> 本规范是 V2.0 Super-agent 架构的命名基准；旧文档逐步迁移，迁移期允许别名。

---

## 零、道门语境

**碧游宫是一个道门，不是朝廷，也不是天庭。**

这决定了整套命名的基调：

- 道门里的任务叫 **师门任务**，不叫「道旨」「圣旨」「任务诏书」。
- 道门里的授权叫 **师门令**，由掌门/长老签发，不叫「法旨」「诏书」。
- 道门里的规则叫 **门规**，不叫「天条」「王法」。
- 道门里接事、收帖、传讯的入口叫 **知客堂**，不叫「天听」「朝堂」。
- 道门里收到的一件事叫 **缘起**，不叫「天象」「奏折」。
- 道门里把任务交给弟子叫 **派差**，弟子 **领命** 后去办。
- 道门里的弟子统称 **仙徒**；**内门 = PC 端**，**外门 = 移动端**。
- 「准圣 / 散仙」作为节点名退役；「准圣」保留为道行第八境。
- 仙徒自身的能力叫 **神通**，可调用的外部工具叫 **法宝**。
- **掌门、长老、首座、知客** 只指人/角色，不指软件组件；软件组件用阵眼、阵图、灵脉等。

一句话：**碧游宫是师门，阵眼是主持阵法的执事，仙徒是领命办事的门人。**

## 一、命名分层

| 层级 | 用途 | 示例 |
|---|---|---|
| L1 叙事层 | 产品定位、对外介绍、UI 大标题 | 碧游宫、万仙阵、阵眼、仙徒、师门任务 |
| L2 组件层 | 架构图、模块名、运维文档 | 山门、阵图、灵脉、道鉴、碧游宫客户端、巡阵 |
| L3 协议层 | 代码、API、数据库、日志字段 | `agent_card`、`ticket`、`mandate`、`assignment`、`report` |

规则：

1. 一个概念只保留一个规范中文名；旧名只作为迁移别名。
2. 叙事名可以仙侠化；错误信息、运维告警、API 文档用平实语言。
3. 代码与协议不出现中文标识符；中文名只用于展示与说明。
4. 新增概念必须先进入本表，再进入 PRD / 设计 / 代码。

## 三、Super-agent 领域概念

| 规范名 | 英文 / 代码 | 定义 | 关键规则 |
|---|---|---|---|
| **知客堂** | Source | 道门接事、收帖、传讯的入口子系统 | 保存读取位置与身份；重启不重放 |
| **信源** | Source instance | 一个具体来源配置 | 例如灵脉、碧游宫客户端、定时值守、IM |
| **缘起** | Trigger | 一件进入道门的事端；一条不可变事件 | 幂等；同一条缘起重复受理只生成一个师门任务 |
| **因果线** | Thread | 同一任务/话题下的事件流 | 同一因果线同时只跑一个观星 |
| **观星** | Eval | 研判：Gate + Assessment | 决定是否立师门任务；不持有状态 |
| **门规** | Policy | 道门戒律、准入与评估规则 | 变更影响在途师门任务时，只下发通知，不撤销师门令 |
| **师门任务** | Ticket | 道门内一个被授权的差事/工作单元 | 只有观星能创建；有独立生命周期 |
| **师门令** | Mandate | 掌门/长老签发的授权：范围、期限、强度、法宝、数据边界 | 不可变；扩大范围必须新开师门任务 |
| **功德殿** | Task Hall | 师门任务交接处（概念先定） | 任务张贴、领命、交接、验收、记功德；实现形态待后续讨论 |
| **观星台** | Observe / Approval | 碧游宫客户端内的观测与定夺页 | 看气机、因果线、待定夺任务；不是客户端总名 |
| **派差** | Assignment | 把师门任务交给某个仙徒；弟子领命后执行 | 一个师门任务可多次派差；派差状态独立 |
| **回禀** | Report | 仙徒向阵眼汇报的状态 | progress / waiting / ready / blocked / failed / dropped |
| **传音** | Channel | 回复到原入口的写通道 | 师门任务可持有多个传音 |
| **因果订阅** | Subscription | 因果线与师门任务的多对多订阅 | 后续缘起直达仙徒，不再经阵眼 |
| **洞府** | Session / Workspace | 仙徒执行任务的隔离会话与工作目录 | 一个师门任务一个洞府；可恢复、可重派 |
| **神识** | Context / Memory | 仙徒或阵眼的上下文与记忆 | 与算力分离；可持久化 |
| **仙箓** | Agent Card | 仙徒的身份与能力卡 | 身份、神通、法宝、模型、限额、位置、状态 |
| **玉册** | Registry | 仙徒与信源的注册表 | 心跳、租约、能力索引 |
| **因果簿** | Ledger | 师门任务、派差、回禀、决策的账本 | 审计与恢复的依据 |
| **藏经阁** | Artifact Store | 产物与知识归档 | 道果、报告、证据、附件 |
| **结界** | Sandbox | 单个任务/仙徒的执行边界 | 法宝权限、文件范围、网络范围 |
| **护山大阵** | Security perimeter | 集群整体安全边界 | 内网、鉴权、入口隔离 |
| **符令** | Credential / Token | 道门令牌；调用山门或阵图的凭据 | 不落明文；不入日志 |
| **命灯** | Heartbeat / Lease | 仙徒存活与租约信号 | 灯灭则巡阵介入 |
| **巡阵** | Watchdog | 异常监督与恢复 | 超时、失联、重派、孤儿清理 |
| **道录** | Logs / Audit | 运行日志与审计流水 | 脱敏；可追溯 |
| **气机** | Metrics | 指标读数 | 对应 Prometheus 指标 |
| **道果** | Result / Artifact | 任务产物与聚合结果 | 可验收、可归档 |
| **定夺** | Human approval | 人对高风险动作的批准/否决 | 写操作、重启、外发前必须定夺 |

### 3.1 根骨与道行

> **根骨 = 先天形态（硬件/运行时）；道行 = 后天修为（能力等级）。派差看道行与神通，不看根骨。**

| 术语 | 含义 | 示例 |
|---|---|---|
| **根骨** | 硬件与运行时形态 | 内门（PC + Ollama）、外门（安卓 + llama.cpp） |
| **道行** | 能力等级 | 人仙 → 地仙 → 天仙 → 玄仙 → 金仙 → 太乙金仙 → 大罗金仙 → 准圣 → 混元 |
| **功德** | 任务贡献，晋升依据 | 完成师门任务、通过道鉴、复核他人道果 |
| **仙箓** | 记录根骨、道行、神通、法宝、限额 | 每个仙徒一张，随道行更新 |

**道行九境**：

| 境 | 名称 | 能力范围 | 可接品阶 |
|---|---|---|---|
| 1 | 人仙 | 基础问答、分类、OCR、Embedding | 黄阶 |
| 2 | 地仙 | 摘要、翻译、单步法宝 | 黄 → 玄 |
| 3 | 天仙 | 多步推理、只读法宝 | 黄 → 地 |
| 4 | 玄仙 | 复杂诊断、多法宝 | 黄 → 天 |
| 5 | 金仙 | 跨文档、代码、运维复杂任务 | 黄 → 宇 |
| 6 | 太乙金仙 | 高难任务、复核、有限写 | 黄 → 宙 |
| 7 | 大罗金仙 | 专家级任务、全局复盘 | 黄 → 洪 |
| 8 | 准圣 | 顶级仙徒、护道、跨域复核 | 黄 → 荒 |
| 9 | 混元 | 阵眼/掌门/最高授权（保留，不轻易派差） | 黄 → 荒（全部） |

> **高阶可接所有低阶任务**，但「可接」只是资格，不是优先权；派差仍按「高阶不轻用」优先低阶合格仙徒。

> 根骨决定**上限**与可用神通，道行决定**当前能接什么**。外门仙徒也可以靠功德晋升；内门仙徒也可能道行尚浅。这就是「不问根骨」。

### 3.2 任务品阶与风险

**品阶 = 难度（需要多高的道行）；风险 = 副作用（需要多大的授权）。两者必须分开。**

| 品阶 | 最低道行 | 典型任务 |
|---|---|---|
| **黄阶** | 人仙 | 问答、分类、OCR、Embedding |
| **玄阶** | 地仙 | 摘要、翻译、单步法宝 |
| **地阶** | 天仙 | 多步诊断、文档审查 |
| **天阶** | 玄仙 | 复杂诊断、跨文档推理、有限写 |
| **宇阶** | 金仙 | 跨系统分析、代码/运维复杂任务 |
| **宙阶** | 太乙金仙 | 长链路任务、高难推理、复核 |
| **洪阶** | 大罗金仙 | 专家级任务、全局复盘、跨域协调 |
| **荒阶** | 准圣 | 宗门级决策、最高风险/最高难度，需掌门/长老定夺 |

> 品阶取「天地玄黄，宇宙洪荒」八字，按由低到高排列：**黄 → 玄 → 地 → 天 → 宇 → 宙 → 洪 → 荒**。
> 协议用 `task.tier: 1..8`，避免「黄 / 荒」同音造成的歧义。

| 风险 | 含义 | 授权要求 |
|---|---|---|
| **清修** | 只读，无副作用 | 师门令可只读法宝 |
| **入世** | 有限写、可回滚 | 师门令 + 定夺 |
| **破阵** | 重启、变更服务 | 师门令 + 护道 + 定夺 |
| **传道** | 外发、对外通信 | 师门令 + 定夺 |

示例：

- 「诊断节点温度过高」= 地阶 + 清修：需要天仙道行，只读。
- 「重启某个节点」= 黄阶 + 破阵：难度不高，但必须授权与定夺。
- 「跨文档根因分析」= 天阶 + 清修：难度高，但只读。

### 3.3 派差规则

1. **不越阶**：`仙徒道行 < 师门任务最低道行` 时禁止接取；低阶仙徒不得接高阶任务。
2. **可低接**：`仙徒道行 > 师门任务最低道行` 时允许接取，高阶可接所有低阶任务；但这是资格，不是优先权。
3. **不越权**：风险等级必须在师门令授权范围内；破阵/传道必须定夺，必要时护道。
4. **高阶不轻用**：低阶任务优先派给刚好够用的仙徒；高阶仙徒留给高阶任务，避免浪费。
5. **无可用则悬赏**：没有合格仙徒时，师门任务进入 **悬赏** 状态，通知功德殿；不得静默降阶派给低阶仙徒。
6. **动态道行**：派差读取玉册中最新仙箓；晋升/降阶后立即生效。
7. **护道复核**：洪阶/荒阶、破阵、传道任务的回禀，需高阶仙徒或长老护道后才能结道果。
8. **不抢占（V2）**：高阶任务到达时，若高阶仙徒正执行低阶任务，高阶任务进入 **候差**，低阶任务继续；候差队列按品阶从高到低、截止时间排序；仙徒空闲时优先接高阶候差。超过期限通知功德殿，必要时由长老定夺中断低阶任务或转悬赏。

### 3.4 道行精进

- **功德来源**：完成师门任务（按品阶、风险、质量加权）、通过道鉴、复核他人道果。
- **功德入账**：只有验收通过才记功德；交接、回禀、口头完成都不入账。
- **晋升条件**：功德达标 + 成功率达标 + 道鉴通过 + 长老定夺；门槛写在门规。
- **仙箓更新**：晋升后更新道行、可接品阶、神通、法宝与限额；玉册立即刷新。
- **根骨上限**：内门根骨上限较高，外门较低；但只影响上限，不影响日常派差判断。
- **回落**：长期失败、回滚、质量不达标可标记「道行不稳」或降阶；是否降阶由门规决定。
- **成长来源**：任务实践、道鉴结果、模型/法宝升级、长老传功。

### 3.5 神通与法宝

> **神通 = 仙徒自身的能力；法宝 = 仙徒可调用的外部工具。**

| 术语 | 英文 / 代码 | 含义 | 示例 |
|---|---|---|---|
| **神通** | `skills` / `capabilities` | 仙徒自身具备的能力 | chat、摘要、翻译、OCR、Embedding、代码 |
| **法宝** | `tools` | 仙徒可调用的外部工具 | `read_file`、`http_get`、`shell`、`restart_service` |
| **本命法宝** | `preferred_tools` | 仙徒最常用/最擅长的法宝（可选） | 读道录、查气机、查因果簿 |
| **法宝权限** | `tool_permissions` | 法宝的使用边界 | 只读、写、重启、外发 |

规则：

1. **神通决定「会不会」，法宝决定「能不能落地」**；派差时两者都要匹配。
2. 仙箓必须声明神通与法宝；未声明的法宝不可调用。
3. 法宝沿用风险四档：清修 / 入世 / 破阵 / 传道；高风险法宝需师门令、定夺或护道。
4. 具体法宝名保留技术名（`read_file`、`http_get`），UI 可显示「法宝：读文件」；不把 `shell` 叫成「诛仙剑」，避免误解。
5. 天赋神通来自根骨（如外门 OCR）；习得神通来自模型、配置或长老传功。

### 3.6 香火与缓存

> 成本领域以技术名为准；UI 可用「香火」表示费用、「灵力」表示 token，协议字段仍用 `tokens` / `cost`。

| 术语 | 英文 / 代码 | 含义 |
|---|---|---|
| **灵力** | `tokens` | 输入/输出 token；缓存命中与未命中分开统计 |
| **香火** | `cost` | 模型调用费用；外部模型按价格表计价，本地模型按算力成本计价 |
| **香火额度** | `budget` | 师门任务、仙徒或单日的费用上限 |
| **缓存命中** | `cache_hit` | 命中 provider prompt cache 的 token |
| **缓存未命中** | `cache_miss` | 未命中的 token |
| **香火节省** | `cache_savings` | 命中相对未命中的费用差 |

规则：

1. **缓存命中/未命中分开计价**，不能只用平均单价。
2. **香火 ≠ 功德**：香火是消耗，功德是贡献。
3. **本地模型不是零成本**：仍要记 token、算力占用、时延与能耗。
4. **师门令必须带香火额度**；超限暂停并请长老定夺，不静默降级。
5. **多仙徒并行前先估算冷/热缓存成本**；冷启动按未命中价估算。

### 3.7 团队协作

| 术语 | 英文 / 代码 | 含义 |
|---|---|---|
| **阵组** | Team | 一个师门任务/因果线下的协作组；阵眼为 Lead |
| **同阵仙徒** | Teammate | 阵组内的仙徒 |
| **任务板** | Task Board | 功德殿/因果簿中的共享任务 DAG |
| **新生** | fresh | 全新上下文，不继承父级历史 |
| **承法** | fork | 继承父级已完成轮次；缓存友好但上下文更重 |
| **传音** | `send_message` | 显式消息；任务变更不自动唤醒 |
| **听候** | `wait_agent` | 等待下一步收件箱 |

规则：

1. **阵组默认关闭**；简单任务单仙徒即可，复杂任务才开阵组。
2. 任务板记录在模型历史之外，只向模型注入紧凑任务视图。
3. 任务变更不唤醒仙徒；需要行动必须**传音**。
4. 新生适合独立并行子任务；承法适合续修/接力，按缓存与 token 成本选择。
5. 分布式阵组依赖命灯租约与超时释放，不依赖共享文件系统。

### 3.8 联阵与开阵

| 术语 | 英文 / 代码 | 含义 |
|---|---|---|
| **单机阵** | Standalone | 不联阵，客户端本地闭环；桌面启动默认此形态 |
| **本地阵眼** | Local router | 只服务本机的阵眼，不广播、不监听联阵 |
| **联阵** | LAN session | 多端在同一局域网组成万仙阵 |
| **开阵** | Host | 用户主动创建联阵会话，开阵后担任阵主/阵眼 |
| **开放阵** | Open room | 无密码阵；同局域网可见，校验通过即入阵 |
| **闭阵** | Closed room | 有密码阵；阵符校验通过即入阵 |
| **寻阵** | Discover | 移动端通过 mDNS + UDP 广播发现局域网阵列表 |
| **阵列表** | Room list | 显示阵名、阵主、版本、人数、是否加密、时延 |
| **入阵** | Join | 校验阵未满、协议兼容、阵未散；开放阵直接入，闭阵校验阵符；均无需阵主确认 |
| **离阵** | Leave | 仙徒主动退出或被命灯判定离线 |
| **阵散** | Room closed | 阵主退出，联阵结束，各端回单机 |
| **阵符** | Passcode | 闭阵的入阵口令，不是账号密码 |

规则：

1. **桌面端启动默认单机**，本地阵眼只服务本机；用户主动开阵后才成为阵主/阵眼。
2. **开阵时二选一**：开放阵（无密码）或闭阵（有密码）。
3. **开放阵**无需阵符，校验通过即入阵；**闭阵**阵符校验通过即入阵；两者均无需阵主确认，阵主可踢人。
4. **无云大厅、无账号、无公网**；只发现同一局域网内的阵。
5. **阵主退出即阵散**；各端回单机，不崩溃、不丢本地数据。
6. **Android 先行，iOS 共用协议与 KMP 核心**，不要求同期交付。

## 五、命名禁则

1. **不用「旨 / 诏 / 天条」等帝王、天庭词**：碧游宫是道门，任务是师门任务，授权是师门令，规则是门规。
2. **不用「封神榜」指任务列表**：封神是终局，师门任务可恢复、可重派。
3. **不用「诛仙阵」指普通编排**：诛仙阵是杀阵，语义过重；普通编排统一叫阵图。
4. **不用「天庭」指控制面**：容易与外部云服务混淆；控制面叫碧游宫，模型入口叫山门。
5. **不用「教主 / 掌门」指 Router**：这两个词只指人；Router 叫阵眼，角色叫主持。
6. **不用「法宝」指模型**：模型是算力与道行，不是法器；**法宝专指工具**，代码仍用 `tools`。
7. **不让「碧游宫」继续单指 NewAPI**：碧游宫是道门/系统，NewAPI 是山门。
8. **不在代码/API/数据库中使用中文名**。
9. **错误信息不强行仙侠化**：例如「山门不可达：连接超时」而不是「天门紧闭，仙路断绝」。
10. **一个概念只保留一个中文名**；别名只出现在迁移表。

## 九、已确认与待确认

### 已确认

- 项目主叙事升级为 Super-agent 架构。
- 碧游宫是道门；任务是师门任务，不是「道旨」。
- **内门 = PC 端，外门 = 移动端**；「准圣 / 散仙」作为节点名退役。
- 根骨与道行分离：根骨定上限，道行定当前能接什么。
- 道行九境与八阶品阶的对应按当前表执行；高阶可接所有低阶任务，但「可接」不等于优先派。
- V2 不抢占：高阶任务等待（候差），低阶任务继续。
- 客户端名为 **碧游宫客户端**；**功德殿** = 师门任务交接处；**观星台** = 客户端内观测/定夺页。
- 观星台保留为碧游宫客户端内的观测/定夺页。
- 功德殿先定概念，实现形态待后续讨论；功德验收通过才入账。

### 待确认

1. 知客堂 = 事件入口、缘起 = 事件，是否确认。
2. 师门令 = 授权、门规 = 规则、派差 = 分派，是否确认。
3. 神通 = 技能、法宝 = 工具，是否确认。
4. 道行九境是否采用，还是先精简为六境（人仙、地仙、天仙、玄仙、金仙、太乙）。
5. 任务品阶 **黄 / 玄 / 地 / 天 / 宇 / 宙 / 洪 / 荒** 是否按此定稿。
6. 风险四档 **清修 / 入世 / 破阵 / 传道** 是否合适。
7. 晋升是否必须经长老定夺，还是允许门规自动晋升；降阶是否启用。
8. 是否在后续版本重命名 `nodes/quasheng` / `nodes/sanxian` 目录，还是永久保留为兼容名。
